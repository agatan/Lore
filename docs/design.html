Implementation reference

Koe 内部設計

LifeLogTextExporterは90秒未満の連続発話を別種の表示項目で区切ってまとめ、TODOは作成日・完了日から抽出します。LifeLogExportSheetはプレビューもbackgroundで4,000文字に制限します。Day paneは縦scroll、予定rowは塗りなしで描画します。LifeLogStoreから対象日以前90日分の話題名を最大100件取得し、LifeLogDerivationServiceが既存プロジェクト名を優先して最大5件生成します。過去本文の送信、追加LLM call、schema変更は行いません。旧commitments fieldは保存互換性のため残し、新規要約は空配列を保存します。

現在のtarget、論理module、runtime flow、永続化、公開adapterをコードに対応づけた実装俯瞰です。設計思想ではなく、変更時にどこを読むかを示します。

3. Processと起動

KoeAppはMenuBarExtraを常設します。KoeApplicationDelegateはwindow sceneの生成有無に依存せずruntimeを起動し、KoeWindowPresenterがmain、settings、life-log mini、all TODOの各windowを一意に所有します。Main windowは3ペインの最低幅1200 ptを満たす1680×960 ptで生成します。Presenterはwindowをkey windowにした後、activation policyの切替がwindow serverへ反映されるまで短く待ち、activeになるまで最大1秒だけactivateを再要求します。明示的な表示要求では対象windowを前面にします。UI、menu、hotkeyはAppEnvironmentの同じ表示actionを呼び、同種windowを重複生成しません。AppEnvironmentは@MainActor @Observableのcomposition rootです。

起動時のcaptureRequestedは必ずfalseです。以前のruntime記録意図を設定から復元せず、明示的なUI、hotkey、App Intentだけが新しい記録意図を作ります。

LifeLogWindowとLifeLogMiniWindowは今日を読み込み、初回だけtimeline末尾へscrollします。TODO provenanceは永続化しますが、出典移動用UI stateは持ちません。

終了時は進行中操作をinterruptし、audio writerのcommitと必要なDB保存だけを短時間待ちます。派生処理は起動せず、確定済みchunkは次回起動時に再処理します。20秒deadlineは最終保険です。

通常の音声入力はaudio fileを作りません。履歴にはtext、snapshot、状態、計測値を保存します。

HotkeyMonitorは文字keyを含む組み合わせをRegisterEventHotKeyで標準event dispatcherへnon-exclusive登録します。macOS 26でdispatcherから通知されないことがあるOptionのみ（Option+Shiftを含む）の文字keyは、CGPreflightListenEventAccessで入力監視権限を確認してCGEventTapも併用します。pressStartを単一の押下状態として二経路をdeduplicateし、最初の押下と離上だけをdomain eventにします。同じtapで修飾キー単体と録音中Escを扱います。四つのmonitorは独立して開始します。

DictationCoordinatorのcapture destinationは通常音声入力とボイスメモです。ボイスメモは同じAudioCapture、STT、HUDを使いますが、SessionDraft、LLM、HistoryStore、TextInserterを通らず、確定した生textをLifeLogCoordinator.addMemoへ一度だけ渡します。AppEnvironmentは開始前にlife-log captureの安全な一時停止を待ち、終了結果にかかわらず記録意図に従って再開します。LifeLogMemoComposerの音声ボタンとglobal hotkeyはどちらもAppEnvironment.toggleVoiceMemoを呼び、Viewは準備中と録音中のstateだけを投影します。

5. Life-log flow

Capture request
→
30秒 .m4a commit
→
AudioChunk保存
→
発話検出・rolling preview
→
Durable audioを遅延STT
→
Calendar / Conversation
→
Summary / draft TODO
  • 音声入力とは独立してaudioを連続耐久化し、Life Log STTはadaptiveな発話burstごとのpreviewと確定jobです。
  • Audio chunkは復旧単位です。30秒ごとに加えてburst確定時にもwriter queue上の入力を原子的にcommitし、最終認識は対応するcommit callback後に開始します。Checkpoint後は定期rotationを30秒後へ再設定し、同時rotationによる空chunkを作りません。
  • AdaptiveSpeechSegmenterはUI表示用levelではなく入力signalの線形RMSを使い、起動直後にbackground noise floorを校正して非発話中も更新します。約-50 dBFSの絶対下限とnoise floorに対する差・倍率が250ms継続した場合だけburstを開始し、30秒未満は1.5秒、30秒以上は1秒の無音でflushします。Flush時は累積有声時間0.5秒以上かつ有声比率20%以上をSpeechBurstEvidenceの不変条件とし、満たさない候補はSTTとcheckpointへ渡しません。Whisper.cppでは有効な発話の開始1.5秒後から、前のpreviewが完了している場合に1.5秒ごとに直近5秒を認識し、暫定textは永続化しません。
  • Jobは参照audioのcommit後に開始します。Timestampはcapture開始時刻とaudio offsetから導出します。語彙は録音session開始時にsnapshot化し、保存audioの再処理では最新の有効語彙を使います。
  • 音声入力と重なる区間もraw audioと認識済みutteranceを保存します。成功したSessionRecordをtimeline、検索、exportの正本として重なるlife-log utteranceを除外します。Summary/TODOは通常音声入力も重なるlife-log utteranceも使いません。Cancelled/failed sessionではlife-log utteranceを残します。
  • pending chunkは起動後に再処理します。保存済みpeak levelはUI用の正規化levelのまま保持し、その尺度で約-50 dBFS未満の明確な無音chunkを除外します。それ以外も保存audioを線形RMSで同じsegmenterへ戻し、有効なburstだけを個別にSTTへ渡します。
  • Audio保持policyは「処理後削除」を既定とし、「7日」「30日」を選択可能にします。削除可能なのはtranscription_state = transcribedかつprocessing_state = extractedのchunkだけです。「処理後削除」は両状態の保存完了後、「7日」「30日」はさらにcapture_ended_atから指定日数の経過後にfileを削除します。DBのchunk metadataと派生dataは削除しません。
  • LifeLogStoreが処理状態と保持policyから削除可能なaudio URLを決定し、AppEnvironmentはその結果だけをfile systemから削除します。Policy変更時と起動時に同じuse caseを実行し、未処理・失敗chunkを期間だけで削除しない不変条件を一か所に置きます。
  • ContinuousAudioCaptureは実際のaudio writerの開始・停止を通知します。LifeLogCoordinatorは旧writerとSTT sessionの終了を待ち、同じprocessの記録意図が残り、sleepまたはボイスメモによる一時停止中でなければbackoff付きで再接続します。マイク権限拒否だけは再試行しません。
  • 設定画面のcalendar手動再取得は、選択日のsnapshot保存、timeline再読込、月間activity更新を一つのuse caseとして実行します。発話と予定は前後2分で関連付け、conversationは90秒の無発話で分割します。
  • 設定間隔で差分がある場合、またはSummary viewの手動要求時に、その日のlife-log発話、memo、予定からsummaryとdraft TODOをatomicに再生成します。手動要求は差分と間隔を無視します。録音停止、app終了、ボイスメモ、sleep、再接続は派生を開始しません。
  • 既定promptは根拠のある会議文脈、話題、決定・未決事項、検討の流れ、次の行動をMarkdown日報へ構成し、事実を補いません。JSONのsummary fieldへMarkdownを保持し、UIはMarkdownとして描画します。失敗時は既存summaryとdraft TODOを保持します。
  • LifeLogDerivationServiceにはsummaryの基準時点を渡します。予定を終了済み、進行中、これからに分類し、未来予定を過去形にしません。日付変更時の定期finalizeは差分がなくても前日の全予定を含むfinal summaryを再生成します。

6. Engines

通常音声入力とボイスメモはSpeechAnalyzerStt固定です。Life logのpreview・確定jobだけをSpeechAnalyzerまたはlocal download済みwhisper.cppから選びます。Audioは送信しません。

WhisperCppSttはLarge v3 Turbo Q5_0 574 MBを既定とし、非Turbo Large v3 Q5_0も選べるcatalog、download、cancel、SHA-256検証、削除を所有します。公式XCFrameworkのC APIをprocess内から直接呼び、GGML modelをMetalとCPUで実行します。Core ML modelとANE specialization、Homebrewや外部CLIへの依存は持ちません。Decode時はspecial tokenを出力せず、engine境界でもcontrol/timestamp tokenを除去します。Read/UI側の補正や既存dataの自動書換えは持ちません。

WhisperCppSttは同じmodelの推論contextを共有し、context handleの排他境界で推論と結果読取りを直列実行します。Control/timestamp tokenと、独立した文として現れる既知の定型hallucination「ご視聴ありがとうございました」はengine境界で除去し、後続する実発話は保持します。LifeLogCoordinatorはSpeechBurstEvidenceが有効になった発話だけを対象に、発話検出から1.5秒後、前のpreviewが完了していれば1.5秒ごとに直近5秒のsnapshotを同じengineへ渡し、ephemeralなliveTranscriptだけを更新します。実行中previewへ新しいsnapshotを重ねず、burst確定時はpreviewのcancel完了後に最終認識を優先します。Preview失敗はlogへ残しますがchunkをfailedにしません。有効なburst確定時だけContinuousAudioCaptureへcheckpointを要求し、永続化済みaudioによる最終認識だけを正本として保存します。

Main/mini timelineはscroll geometryから末尾表示を保持し、初回と追従中のitem追加だけ末尾へscrollします。利用者操作またはsource navigationで末尾を離れた場合は追従を止め、末尾へ戻った時だけ再開します。

FormattingPromptは通常textか、名前とfield型を持つ構造化出力contractを明示します。LifeLogDerivationServiceはsummary/TODOのJSON contractを宣言し、model判定を持ちません。GroqLlmはこれを温度0、推論本文なし、選択modelが対応する最小の推論量と最も強いJSON制約へ変換します。GPT-OSSはreasoning_effort = lowとstrict JSON Schema、reasoningを無効化できるmodelは無効化とJSON Object Mode、それ以外は未対応parameterを送らずJSON Object Modeを使います。全経路で同じapp側decodeを最終検証とし、通常の文章変換は温度0とprovider既定の推論量を維持します。

whisper.cpp STT選択はlife logだけに置きます。LLMのprovider/modelは音声入力とlife logで別設定にし、語彙候補のanalysisLlmは常にオンデバイスです。

利用状況の録音時間はDailyRecordingDuration.aggregateで重なる区間を先に統合してから日境界で分割します。音声入力はHistoryStoreの実録音区間、life logはLifeLogStoreのtimelineに採用されたutterance区間を入力とし、LifeLogSpeechProjectionと同じ規則で成功した音声入力と重なるutteranceを除外します。復旧用audio chunkの無音区間や同一区間の重複は利用時間へ加算しません。

DBはApplication Support/Koe/koe.sqlite、whisper.cpp modelと途中downloadはApplication Support/Koe/Models/WhisperCpp/です。既存DBはmigration前と1日1回backupし、最新7fileを保持します。全data削除はbackup、新旧model、途中fileも削除します。

8. 設定、秘密、process間同期

  • AppSettings.StorageをUserDefaultsへ保存しますが、runtimeのcaptureRequestedは永続化しません。
  • whisper.cpp engine/modelとlife log認識言語はlife logだけに置き、通常の音声入力とボイスメモはSpeechAnalyzer固定です。
  • 認識言語の既定値は表示言語を固定hintへ解決し、明示的な自動判定も選べます。
  • GGML model本体と途中downloadは専用directoryへ置き、全data削除に含めます。
  • 表示言語はlife log設定が明示する解決以外ではSTT locale、prompt、保存data、automation contractへ伝播させません。
  • API keyだけはKeychainへ保存し、CLI/MCPによるTODO・prompt変更はappへ通知します。

10. 自動化境界

App Intents、CLI、MCPを公開します。CLI/MCPはKoeAutomationServiceを共有し、日別export、open TODO export、横断検索、TODO CRUD、summary/TODO prompt更新を提供します。App IntentsはAppEnvironment.boot()の完了後に実行します。開始Actionだけはマイクを扱うためforeground mode、その他はbackground modeです。Shortcutsからの実行にはmacOSが検証できるbundle署名が必要なため、buildは有効なApple Development identityを自己署名より優先します。公開commandとtool schemaは外部仕様に列挙します。

11. 並行実行とerror表示

  • UI stateとcoordinatorはMainActor、Calendarはactor、DBはDatabaseQueueで直列化します。
  • 長時間処理は所有Taskでcancelします。
  • 失敗は履歴status、画面、MCPのisError、CLIのstderr/exit 1のいずれかへ出し、本文やsecretをlogへ出しません。

13. Test配置

Tests/KoeKitTestsはnoise floor校正と追従、相対level差による発話開始、1.5/1秒tier、whisper.cppの1.5秒preview cadenceと5秒rolling window、5分flushをdomain testで固定します。make ui-testは本番と別のbundle IDを持つ署名済みKoeUITests.appを別process instanceとして起動して主要CUJを検証します。UI test bundleは専用UserDefaultsとインモリDBを使い、global hotkeyと権限監視を起動しません。E2E runnerは専用bundle ID以外のappを終了せず、本番bundle IDを指定された場合は実行を拒否します。
