3. Processes and launch

LoreApp keeps a permanent MenuBarExtra. LoreApplicationDelegate starts the runtime whether or not a window scene exists, and LoreWindowPresenter is the single owner of the main, settings, and Life Log mini windows. The main window is created at 1680×960 pt, the settings window at 980×720 pt, and the mini window at 460×620 pt. After the presenter shows a window and makes it key, it waits briefly for the activation policy change to reach the window server and requests activation again for at most 1 second until the app is active. WindowActivation switches the app to the regular activation policy while any Lore window is open and back to accessory when the last one closes, so the Dock icon exists only while a window is open. The UI, the menus, and the hotkeys call the same show actions on AppEnvironment and never create a second window of a kind. AppEnvironment is the @MainActor @Observable composition root. It owns the settings, the database, the engines, the hotkeys, the three coordinators (DictationCoordinator, LifeLogCoordinator, SyncCoordinator), LifeLogAIService, and the state projected to the screens.

The launch order is:

  1. Creating AppEnvironment builds AppSettings (after LegacyKoeMigration.migrateDefaults) and EngineRegistry.
  2. The app delegate shows the main window with mainSection = .lifeLog, or the settings section that a UI test requested, and then calls boot().
  3. boot() refreshes permissions and moves legacy Koe Keychain items.
  4. LoreDatabase.openDefault() moves the Koe folder if needed, backs up, and migrates.
  5. LifeLogCoordinator.configure runs and starts reprocessing pending audio chunks in the background.
  6. Built-in modes and the common rules are seeded. Modes, rules, vocabulary, and history are loaded.
  7. History and Life Log audio beyond their retention are deleted.
  8. SyncCoordinator.configure runs.
  9. LoreAppEventDetailsServer starts answering lore-mcp (section 10). The four global hotkeys and the permission watcher start, the login item state is read, and the engine selection is applied.
  10. The Life Log schedule is evaluated.
  11. LifeLogAIService is configured and evaluates the event notes trigger for today.

captureRequested is always false at launch. Lore does not restore an earlier runtime recording intent from saved settings. It only reprocesses pending chunks. Only an explicit action from the UI, a hotkey, or an App Intent, or an enabled schedule, creates a new recording intent.

Scheduled recording has three layers. Domain/LifeLogSchedule is a value with only the weekdays, the start minute, and the end minute. It computes window(containing:) and nextTransition(after:) through Calendar, including windows that cross midnight and DST. Domain/LifeLogCaptureController is a pure state machine that holds whether the schedule started the recording, the start of the window that a manual stop suppressed, and the active pause (section 5.1). From the current time and the recording intent it decides to start, stop, resume, or do nothing. AppEnvironment evaluates it at the end of boot, on a settings change, on wake, and on NSSystemClockDidChange and NSSystemTimeZoneDidChange, and replaces a single Task that sleeps until the next switch time. There is no polling loop for the schedule. A manual start or stop, including the stop that precedes a Life Log or full data deletion, notifies the state machine in setLifeLogCaptureEnabled, and a scheduled start or stop calls the same applyLifeLogCapture transition directly, so it does not count as a user change. Without consent to store audio, the schedule does not start and a banner asks for a manual start.

LifeLogCoordinator holds two days. day is the day selected in the main window, and today is always the current day. reload() loads both, and loads once when they are the same day. LifeLogWindow loads today through followCurrentDay() when it appears and scrolls to the end of the timeline once. LifeLogMiniWindow, the menu bar panel's today counts, and AppEnvironment.currentLifeLogEvent (the "until the current event ends" pause) read today, so selecting another day in the main window never changes them.

On quit, the app delegate interrupts operations in progress and waits briefly for the audio writer commit and the required database writes. The Life Log stop has its own 3-second timeout. Committed chunks are reprocessed at the next launch, which keeps quit fast and the data recoverable. The 20-second deadline is the last resort for an unresponsive OS.

4. Dictation pipeline

DictationCoordinator is the center of the implementation.

Hotkey/UI
  -> fix target app, mode, rules, vocabulary, and engine in SessionContext
  -> AudioCapture + dictation SttEngine (SpeechAnalyzerStt / WhisperCppStt)
  -> save raw transcript as SessionRecord(interrupted)
  -> FormattingPolicy + LlmEngine
  -> TextInserter
  -> completed / fallback / clipboard_only / failed / cancelled
  • HotkeyGestureInterpreter interprets short and long presses, FrontmostAppObserver supplies the target app, and ModeResolver selects the mode.
  • HotkeyMonitor registers a combination that includes a letter key with RegisterEventHotKey, non-exclusively, on the standard event dispatcher. On macOS 26 the dispatcher sometimes does not report letter keys combined with Option only (including Option+Shift). For those, the monitor requires both AXIsProcessTrusted and CGPreflightListenEventAccess and also uses a CGEventTap. It deduplicates the two paths with pressStart as the single pressed state and turns only the first press and release into domain events. The same tap handles modifier-only hotkeys and Esc while the coordinator is busy. The four monitors start independently.
  • SessionDraft holds the progress and measurements of recording, recognizing, formatting, and inserting, and is finalized into a persistable SessionRecord.
  • The raw transcript is saved after speech recognition finishes and before the LLM is called.
  • FormattingPolicy builds the request: the system prompt is the common rules, then the mode instructions, then the vocabulary table, and the user message is the transcript inside <transcript> tags. The mode's language goes only to the speech recognition hint. Mode.llmModel is persisted but the pipeline does not read it. The model always comes from the global setting.
  • FormattingPolicy rejects an output that is empty, has a length ratio to the input outside 0.3 to 2.0 (checked for inputs of 12 characters or more), contains a leakage marker, or has a character-bigram overlap with the input below 0.15. On rejection, timeout, or an unavailable engine, the raw transcript becomes the text to insert, and the record stores the formatting engine as none with the reason in error.
  • TextInserter saves the clipboard, pastes into the target app, and restores the clipboard. On failure it leaves the result on the clipboard.
  • DictationCoordinator.inAppReceiver is an optional in-app destination. AppEnvironment sets it only while the onboarding try-dictation step is shown. When it is set and Lore is the active app at recording start, the session has no target app, ModeResolver falls back to the default mode, and after the record is persisted the coordinator passes the record to the receiver instead of calling TextInserter. The record is marked inserted and saved to HistoryStore like any other dictation.
  • Dictation never creates an audio file.
  • DictationCoordinator has two capture destinations, dictation and voice memo. A voice memo uses the same AudioCapture, speech recognition, and HUD, but skips SessionDraft, the LLM, HistoryStore, and TextInserter, and passes the final raw text to LifeLogCoordinator.addMemo exactly once.
  • Before a voice memo starts, AppEnvironment awaits LifeLogCoordinator.suspendForVoiceMemo, and it calls resumeAfterVoiceMemo whatever the outcome. So the capture span that would produce the same audio as a Life Log utterance never exists.
  • The voice button of LifeLogMemoComposer and the global hotkey both call AppEnvironment.toggleVoiceMemo. The UI projects only isPreparingVoiceMemo and DictationCoordinator.isVoiceMemoRecording. Exclusion and memo saving stay out of the views.
  • After 10 minutes idle, EngineRegistry.unloadDictationEngines releases the dictation whisper.cpp state, the SpeechAnalyzer engine, and the current LLM, and clears the cached capture format.

5. Life Log pipeline

LifeLogCoordinator shares no state with dictation and persists audio through its own ContinuousAudioCapture. Life Log speech recognition runs the selected engine as a rolling preview per adaptive speech burst and as a final job.

capture request
  -> commit a 30-second .partial to an .m4a in the same directory
  -> save LifeLogAudioChunk to the database
  -> finalize the adaptive speech burst range from the input signal
  -> recognize the durable audio range in a deferred job and save timestamped utterances
  -> optional association with the calendar snapshot
  -> reload the timeline and monthly activity

The only LLM path from the Life Log is LifeLogAIService (section 5.2). It never runs inside the capture or transcription pipeline and only reads what the pipeline has saved. Other review and organizing are left to an external general-purpose AI that reads the day export and search through MCP.

  • Before the first start, the user must explicitly consent to local audio storage.
  • An audio chunk is the unit of recovery and retention. It is committed every 30 seconds or when a burst ends. When a burst range spans chunks, the job input is formed after all of those chunks are committed.
  • AdaptiveSpeechSegmenter is a domain policy independent of capture and of the speech recognition adapters. Its input is the linear RMS from AudioCapture.rootMeanSquare(of:), not the log-normalized level shown in the UI. It calibrates the background noise floor during the first second and keeps updating it slowly while nobody speaks. A burst starts only when the input satisfies the absolute floor of about -50 dBFS and the difference and ratio against the noise floor for 250 ms, so faint or steady background noise produces no job. A burst flushes after 1.5 seconds of continuous silence when its voiced time is under 30 seconds and after 1 second at 30 seconds or more. SpeechBurstEvidence holds the invariant that a flushed burst has at least 0.5 seconds of voiced time and a voiced ratio of at least 20%. A candidate that fails it reaches neither speech recognition nor a checkpoint. A burst is flushed for safety when its wall time reaches 5 minutes.
  • After a flush, the job starts only when every audio range it refers to is committed. Result timestamps are the capture start time plus the audio offset, never the processing start time or a clock inside the model. The vocabulary is snapshotted when the recording session starts. Reprocessing of stored audio uses the latest enabled vocabulary.
  • Spans that overlap dictation still store raw audio and recognized utterances. On read, the actual recording span of the dictation (startedAt plus audioDurationMs) resolves the duplication: a successful SessionRecord is authoritative for the timeline, search, and export, and overlapping Life Log utterances are excluded from those projections. A canceled or failed session is not authoritative and the Life Log utterances remain. This priority lives in one shared domain projection, not in the UI or in an adapter.
  • Unprocessed and failed chunks carry a stored state and are reprocessed oldest first after launch. The stored peakLevel keeps the UI's normalized scale, and on that scale chunks that are clearly silent (below about -50 dBFS) or shorter than 1 second are skipped. The rest go back through the same AdaptiveSpeechSegmenter as linear RMS, and only valid bursts are passed to speech recognition one by one. A whole 30-second chunk or a silent span never enters a large model.
  • The audio retention policy defaults to deleting after transcription and offers 7 and 30 days. Only a chunk with transcription_state = transcribed and processing_state = extracted can be deleted. processing_state = extracted means that saving the utterances is complete. The name is reused from an older derived-processing state to stay compatible with stored data. "Delete After Transcription" deletes the file once both states are saved. The day options also wait until the given days have passed since capture_ended_at. The chunk metadata and the utterances in the database are not deleted. AppSettings still decodes an unlimited value saved by an older version, and the picker shows it as a legacy entry.
  • LifeLogStore decides the deletable audio URLs from the processing state and the retention policy, and AppEnvironment only removes those files. The same use case runs on a policy change and at launch, so the invariant that unprocessed and failed chunks are never deleted by age alone lives in one place.
  • ContinuousAudioCapture reports the real start and stop of the audio writer through onRunningChanged, and only LifeLogCoordinator.isCapturing is projected to every UI as the actual recording state. On an audio configuration change it commits the writer safely. If captureRequested of the same process remains and capture is not paused for sleep or a voice memo, it reconnects to the new input configuration with backoff. Only a denied microphone permission is not retried. Finalized burst jobs continue and retry independently of capture reconnection.
  • AudioCapture and ContinuousAudioCapture each keep one AVAudioEngine through ReusableInputEngine and reuse it while the default input device stays the same and no configuration change has been posted. Creating a new engine makes macOS wait for a Bluetooth audio format change on first access to inputNode. While the other capture already holds the same Bluetooth device, that wait times out after about 3 seconds on the main thread, which drops the start of the recording, the start sound, and hotkey handling. A new engine is created only after the default input changes, a configuration change, or a failed start.
  • The calendar stores a minimal snapshot of the selected calendars from EventKit. The manual refresh in Settings also goes through LifeLogCoordinator.refreshCalendar, which saves the snapshot of the selected day, reloads the timeline, and updates the monthly activity as one use case. Association with utterances allows 2 minutes before and after.
  • Event details are read on demand and never persisted. CalendarEventDetails is a domain value keyed by the EventKit eventIdentifier and the occurrence start, holding the notes, location, URL, organizer, attendees (CalendarAttendee), canceled flag, calendarItemExternalIdentifier, and the ConferenceLink that its initializer extracts. ConferenceLink.first(url:location:notes:) is a pure function: it scans the fields in the order URL, location, notes, finds links in each with NSDataDetector, and returns the first one whose host and path match Google Meet, Zoom, Microsoft Teams, or Webex, normalized to https. CalendarProvider.details(start:end:selectedCalendars:) maps the EventKit events of a range, and CalendarProvider.details(eventID:startsAt:) reads a one-second window around the start and picks the occurrence with the same identifier and start ([CalendarEventDetails].occurrence(eventID:startsAt:)), because every occurrence of a repeating event shares the identifier and EKEventStore.event(withIdentifier:) returns the first one. Both return nothing without full calendar access and never request it. The app reads details through LifeLogCoordinator.eventDetails(for:), which goes through the CalendarEventDetailsReading protocol. The DEBUG screenshot demo replaces the reader with DemoCalendarEventDetails, which returns fixed details for the demo events.
  • The main window inspector shows the selected event's details through LifeLogCoordinator.eventInspector, an EventInspectorModel (App, @MainActor @Observable). Its one state is selection: EventSelection?, where EventSelection pairs the snapshot with an EventDetailsLoad (loading, loaded(CalendarEventDetails), or unavailable), so no separate optional can disagree with it. select(_:load:) replaces the selection with loading for the new occurrence at once, cancels the previous load, and applies a result only while the selection is still the same occurrence (event identifier and start), so a late result for an earlier event is dropped even when its reader ignores cancellation. Selecting the occurrence that is already selected does nothing. LifeLogCoordinator.select(date:) and reload() call reconcile(with:) with the day's events: it replaces the selected snapshot with the fresh one of the same occurrence and clears the selection when the occurrence is no longer on the day. LifeLogCoordinator.selectEvent(_:) passes eventDetails(for:) as the loader. Nothing is persisted.
  • Domain/EventDescriptionText holds the pure text rules of the inspector: plainText(from:) turns a description into plain text (a string with no HTML tag is returned as is; otherwise tags are removed, br, p, div, li, tr, headings, and similar end a line, li starts with "•", script and style content is dropped, whitespace in the markup collapses, and numeric and the common named character references are decoded; <a href> whose text differs from the address becomes "text (address)"), preview(_:maxLines:maxCharacters:) cuts at a line limit and then at the last whitespace within the character limit and reports whether it cut, and links(in:) finds http and https ranges with NSDataDetector. It does not use NSAttributedString HTML import, which needs WebKit and the main thread. Domain/EventGuestList splits the attendees into people (person, group, unknown) and rooms (room, resource), maps CalendarParticipationStatus to the four responses (accepted, declined, tentative, noResponse for pending, unknown, and none), and counts people per response.
  • Joining a meeting. JoinableMeeting(event:details:) pairs a snapshot of LifeLogCoordinator.today with its details and fails for an all-day, declined, or canceled event and for one without a ConferenceLink. UpcomingMeetings is the pure decision over those meetings: entries(at:) returns the offers at a moment (started within the next 10 minutes or in progress, upcoming ones by start, then in-progress ones by latest start) with a MeetingCountdown (startsIn(minutes:) rounded up, or inProgress), boundaries(after:) returns every later moment at which the entries change (each countdown minute, the start, the end), and remindersDue(at:excluding:) and nextReminder(after:) give the one-minute notification. AppEnvironment rebuilds upcomingMeetings whenever today changes (observation tracking) and after an EKEventStoreChanged, reading details through LifeLogCoordinator.eventDetails(for:). At launch, on wake, and after an EKEventStoreChanged, it saves today's snapshot of the shown calendars first (saveTodayCalendarSnapshot), only with calendar access and never in the screenshot demo. The views put boundaries(after:) into a TimelineView(.explicit(...)), so the countdown wakes once per boundary and never reads the database. AppEnvironment.joinMeeting(_:) passes link.url to NSWorkspace.open and touches no capture state. In the DEBUG screenshot demo and the UI test bundle it logs the URL (LoreLog.ui, category ui, "Join opened") instead of opening it. With the notification setting on, one Task sleeps until nextReminder(after:), posts the due reminders, remembers their ids for the process, and sleeps again.
  • CalendarEventLink (Domain) builds the addresses that open an event elsewhere. calendarApp(eventID:) is ical://ekevent/<percent-encoded eventIdentifier>?method=show, which the Calendar app handles. googleCalendar(externalIdentifier:calendarEmail:occurrenceStart:isAllDay:) returns nil unless the external identifier is <id>@google.com with a Google event id (0-9 and a-v, 5 to 1024 characters) and the calendar email has the shape of an email address. It returns https://calendar.google.com/calendar/event?eid=<eid>, where eid is the unpadded URL-safe Base64 of <event id> <calendar email>. For an occurrence of a repeating event the event id is <id>_<original start> (yyyyMMdd'T'HHmmss'Z' in UTC, or yyyyMMdd for an all-day event). CalendarProvider passes the calendar title, or else the account (source) title, as the calendar email when it is an email address on a CalDAV account, and the occurrenceDate of a repeating or detached event, and stores the result in CalendarEventDetails.googleCalendarURL. The shape of the identifier and the address have not been checked against a real Google account yet.
  • The participation filter is one rule in CalendarParticipationStatus (Domain). isShownWhenAttendingOnly is true for none, accepted, and pending. LifeLogStore.day and activity build their SQL IN list from it, so the timeline, the mini window, the day export, and the range reads of the automation service cannot disagree. isParticipating (none, accepted) is the stricter rule that automatic Life Log AI notes use while the filter is on, so an unanswered invitation never starts notes on its own.
  • The "No Response" tag reads CalendarEventSnapshot.participationStatus == .pending. Each calendar read replaces the day's snapshot, so the tag follows the latest response without a separate state.
  • The stream is closed before sleep and reconnects with backoff after wake only if the recording intent remains.

5.1 Capture decisions: schedule, pause, and event holds

The recording intent stays in LifeLogCoordinator.captureRequested. Whether the microphone may run while that intent exists is decided in the domain and applied by AppEnvironment.

  • LifeLogCaptureController (Domain) is the one state machine for who owns the intent and whether it is paused. It holds ownsCapture (the schedule started the recording), suppressedWindowStart (the user stopped inside a window), and pause: LifeLogPause? (resumesAt and the owner to restore). evaluate(schedule:now:hasCaptureIntent:) returns start, stop, resume, or none. An expired pause yields resume. A schedule window that ends while the schedule owns a paused recording yields stop and drops the pause. A window that starts during a pause yields none, because a pause counts as a recording intent. nextWake(schedule:now:) is the earlier of the next schedule transition and the resume time.
  • LifeLogPauseLength turns a menu or App Intent choice into a resume time. "Until the current event ends" uses the end of the timed event in progress in today's timeline snapshot and is unavailable without one.
  • LifeLogRecordingExclusions (Domain) holds the "Never Record" calendar titles and the single events marked "Do Not Record". A single event is keyed by the EventKit event identifier and its start time, so one occurrence of a recurring event can be marked alone. It answers which timed event in progress holds capture, the next start or end among held events, and it prunes marks whose event ended. All-day events never hold.
  • LifeLogCoordinator.setHold(_:) takes a LifeLogCaptureHold? (paused(resumesAt:) or event(title:endsAt:)). A hold works like the sleep and voice memo suspensions: it keeps captureRequested, stops the writer so the current chunk is committed, and blocks the start and retry paths until the hold is cleared. The status text and the menu bar icon read the hold from the coordinator.
  • AppEnvironment.applyLifeLogSchedule evaluates the controller, applies the action, sets the hold (a pause wins over an event hold), saves lifeLogPause to the settings, and sleeps until the earliest of nextWake and the next held-event boundary. It runs at launch, on wake, on clock and time zone changes, after every user action, and when the event list changes.
  • When exclusions are not empty, AppEnvironment reads the events of every calendar from 12 hours before to 24 hours after now through LifeLogCoordinator's CalendarProvider, without asking for access, at launch, on wake, on EKEventStoreChanged, after the marks change, and every 15 minutes. The events stay in memory only.
  • At launch, a stored LifeLogPause restores the controller and the recording intent with the pause hold. Consent was given before the pause, because a pause needs a recording intent. A UI test bundle launch does not restore it, as it does not start the schedule.

5.2 Life Log AI

event end / launch / wake / calendar refresh / transcription finished
  -> EventNotesTrigger.decide for each event of today (pure)
  -> LifeLogAIService.generate(kind: .eventNotes, scope: occurrence)
       -> guard LifeLogAISettings (on, cloud consent)
       -> EventNotesPolicy.input: utterances and memos inside the range, minus excluded ranges
       -> EventNotesPolicy.prompt -> LlmEngine.complete -> EventNotesPolicy.parse
       -> LifeLogStore.save(generatedNote:)
  -> reload the timeline, post the notification

digest time / launch / wake / transcription finished / settings change
  -> DailyDigestTrigger.decide for yesterday and today (pure)
  -> LifeLogAIService.generate(kind: .dailyDigest, scope: .day(key))
       -> same guard
       -> DailyDigestPolicy.input: the day's events, fresh event notes, memos, utterances, minus excluded ranges
       -> DailyDigestPolicy.prompt (reduction rule) -> LlmEngine.complete -> GeneratedNoteResponse.parse
       -> LifeLogStore.save(generatedNote:)
  -> reload the timeline, post the notification with the day's numbers
  • Domain/LifeLogAISettings is the persisted setting: isEnabled, backend (a FormattingBackend), model, confirmedCloudBackend, excludedCalendars, eventNotesTrigger and dailyDigestTrigger (each a GenerationTriggerMode, automatic or manual), dailyDigestMinute (minutes after midnight, 18:00 by default), notifiesWhenEventNotesReady, and notifiesWhenDailyDigestReady. sendPermission returns .allowed only when the switch is on and, for a cloud backend, confirmedCloudBackend equals the backend. Changing the backend in Settings clears the confirmation unless the user confirms the new cloud backend.
  • Domain/GeneratedNote is the stored note: id, kind (eventNotes or dailyDigest), scope (.event(EventOccurrence), where the occurrence is the event identifier plus the day key of its start, or .day(String) for a digest), the source range (the whole day for a digest), the provider and model, createdAt, the source utterance and memo identifiers, omittedSourceCount (records left out to fit the input limit), and sections of summary (digest only), commitments, requests, and decisions, which describe the user's own side: what the user took on, asked others for, and decided. searchText is the item texts joined by line breaks, stored for search. Each item has text, an optional owner (on a request, the person the user asked), and sources, the timeline item identifiers (u-<id>, m-<id>) it came from. staleReasons (eventChanged, sourcesDeleted) is not stored. LifeLogStore computes it on every read from the current event snapshot and the existence of the sources. calendar_event_snapshots keeps one row per occurrence, so the check reads the row with the note's event identifier that starts on the note's scope day, and a missing row marks the note eventChanged.
  • Domain/EventNotesPolicy builds the request input and the prompt and parses the response. The input contains only utterances whose start, and memos whose creation time, fall inside the event range, minus any utterance or memo that overlaps the range of an excluded event (all-day included) or of an event in an excluded calendar. The events of excluded calendars come from LifeLogAIService.Dependencies.excludedCalendarEvents, which reads EventKit directly, because the snapshot holds only the calendars shown in the timeline. Sources (GeneratedNoteSource, kind utterance, memo, event, or note) are labeled S1, S2, … in time order. Each source is one line: the label, the time (HH:mm, or HH:mm-HH:mm for an event), and the text. An utterance has no kind word, because utterances make up most lines of a day; any other kind puts event:, note:, or memo: before its text. The input is cut to the engine's inputCharacterBudget by keeping the earliest sources that fit, only the labels that were sent count as sources, and the number left out becomes omittedSourceCount. The prompt is English, asks for one item per line (COMMIT (S1): …, ASK (S2) [person]: …, DECIDE (S3): …, or NONE), requires every item to cite labels, states that only the user's microphone was recorded, that memos are the user's and utterances carry no speaker, keeps only items the sources show to be the user's own, and forbids invented content. A line format rather than JSON, because the on-device model often emits malformed JSON. GeneratedNoteResponse.parse is shared by both kinds and takes the section kinds a kind may contain, so SUMMARY (S1): … is read only for a digest. The parser reads the lines it recognizes, drops items without a known label, maps labels to timeline item identifiers, and records the sources that remain. An answer with no recognized line and no NONE is an error. minimumSpokenCharacters is 120.
  • Domain/EventNotesTrigger.decide is a pure function of the event, the current time, the settings, the exclusion, whether a note exists, the spoken characters in range, and the start of the oldest audio that is not transcribed yet. It also takes whether the user deleted the note of the occurrence. It returns .generate, .waitUntil(Date) (the event has not ended, plus a 15-second settle time), .waitForTranscription, or .skip(reason). The look-back is the day that contains now minus the settle time, so an event that ends at midnight still counts. The service evaluates that day and today, and only the events that pass the participation filter.
  • Domain/DailyDigestPolicy builds the digest input from one LifeLogDay read without the participation filter. Excluded ranges are computed as for event notes. Event titles come from the events that pass the participation filter and are not excluded. For each such event with event notes that have no stale reason, the note items become note sources and the utterances inside the event range are dropped. Memos stay. spokenCharacters counts every utterance outside excluded ranges, before the replacement, and minimumSpokenCharacters is 300. reduce(_:budget:) is the reduction rule: tiers in the order event, note, memo, utterance; a tier that fits is sent whole; in the first tier that does not fit, every k-th source in time order from the first, for the smallest k that fits; lower tiers are dropped. The sent sources are relabeled in time order.
  • Domain/DailyDigestTrigger.decide is pure, like EventNotesTrigger.decide, and returns the same GenerationDecision. Its inputs are the day, the current time, the day's digest time, the settings, whether a digest exists or was deleted, the spoken characters, and the oldest untranscribed audio. Only today and yesterday pass the look-back. digestTime(for:schedule:minute:) is the end of the LifeLogSchedule window that starts on the day when the schedule is on and the day is scheduled, otherwise the day at dailyDigestMinute.
  • LifeLogAIService (@MainActor @Observable) is the single entry point. generate(kind:scope:) checks sendPermission first and throws before touching any text when sending is not allowed. Only then does it gather the input, call the engine from EngineRegistry.standaloneEngine(backend:model:), and save the note with an upsert on (kind, scope_key). It keeps one task per scope key, so concurrent triggers for the same occurrence produce one request. Failures are kept per scope key in failures for the UI's "Retry", and an automatic run does not retry a failed occurrence in the same process. The daily request count is stored in meta under life_log_ai_requests as yyyy-MM-dd count.
  • The trigger runs at launch, on wake, after a calendar refresh, after transcription finishes, on a settings change, and in a single Task that sleeps until the next decision time (an event end plus the settle time, or 2 minutes while transcription is pending). There is no polling loop otherwise. Before deciding, it saves today's calendar snapshot when calendar access is granted. LifeLogCoordinator.oldestUntranscribedAudioStart() combines the burst in progress in the live session (its start minus 2 seconds of pre-roll) with stored chunks outside the live session that are still captured or not yet extracted. Failed chunks do not block.
  • EngineRegistry.standaloneEngine creates a fresh engine for each Life Log AI request and each connection check in Settings from the same factory that the formatting engines use, so neither changes the formatting model. Ollama and LM Studio use their fixed localhost base URLs.
  • evaluateDailyDigest() runs at the same moments as the event notes trigger, decides for yesterday and today, and keeps its own sleeping Task until the next digest time (or 2 minutes while transcription is pending). An automatic failure is not retried for that day in the same process.
  • System/NotificationPresenter posts the "notes are ready" notification with the event identifier and day in userInfo. A click calls AppEnvironment.showLifeLogEvent, which opens the main window on that day and highlights the event. The "digest is ready" notification carries only the day. Its body is the talk time and the event and memo counts from LifeLogDaySummary, and a click calls AppEnvironment.showLifeLogDigest, which opens that day at the digest. It also posts the meeting reminder in the meeting-join category with a "Join" action and the link in userInfo. The "Join" action and a click on the reminder call AppEnvironment.openJoinLink. The UI test bundle and the screenshot demo do not post notifications.
  • The morning sheet: when LifeLogWindow appears, AppEnvironment.presentMorningDigestIfNeeded() asks LifeLogAIService.takeMorningDigest(), which reads yesterday's digest and the meta key daily_digest_presented_day. When the digest exists and the key is not that day, it writes the key first and returns the digest, which becomes morningDigest and the window's sheet. Writing first makes it appear once even if the window closes at once.

EngineRegistry selects a SttEngine for dictation and voice memos, and another for Life Log previews and final jobs, each from SpeechAnalyzerStt or WhisperCppStt. A session or job uses the engine it started with until it ends. LlmEngine is selected only for dictation formatting.

WhisperCppStt puts the model catalog, download, cancel, SHA-256 verification, and deletion behind one boundary. The catalog is Large v3 Turbo Q5_0 (574 MB, the default), Large v3 Q5_0 (1.08 GB), and Small Q5_1 (190 MB).

  • WhisperModelCache loads the GGML weights once per file in the process and frees them when every state lets go.
  • EngineRegistry holds separate WhisperCppStt instances for dictation and for the Life Log. Each owns its inference state, so the two uses do not wait for each other. Inference and result reads on one state run serially through the actor and the state handle. A running job keeps its state and weights until it completes.
  • Dictation starts preparing the state from captureFormat without delaying recording. The Life Log state is released when recording has stopped. A finished download alone does not load an inference state.
  • WhisperInputPolicy trims leading and trailing silence before the audio is passed, and the trimmed length is added back to segment offsets so they match the stored audio. The same policy fits the vocabulary prompt into the token limit in list order and removes a segment that only repeats the whole prompt.
  • The engine calls the C API of the official XCFramework in process and runs the GGML model on Metal and the CPU. It has no Core ML model, no ANE specialization, and no dependency on Homebrew or an external CLI.
  • Decoding emits no special tokens. At the engine boundary, control and timestamp tokens and the known boilerplate hallucination "ご視聴ありがとうございました", when it appears as a standalone sentence, are removed before the result becomes a domain event. Real speech that follows is kept. There is no correction on the read or UI side and no automatic rewrite of existing data.
  • The model download request to Hugging Face carries no audio, transcript, or user data.

LifeLogCoordinator previews only speech whose SpeechBurstEvidence became valid. Starting 1.5 seconds after speech is detected, and every 1.5 seconds while the previous preview has finished, it passes a snapshot of the latest 5 seconds to the same SttEngine and publishes the result only as the ephemeral liveTranscript. It never stacks a new snapshot on a running preview, and when the burst ends, the final recognition takes priority after the preview's cancellation completes. A preview failure is logged without changing the reprocessing state of recorded audio. Only a final recognition failure counts as a chunk failure. Only a valid burst end asks ContinuousAudioCapture for a checkpoint, which atomically commits the input on the writer queue and starts the next file. The final result is saved with timestamps after the commit callback of the audio it refers to. After a checkpoint, the periodic rotation is reset to 30 seconds later, so a simultaneous rotation never creates an empty chunk.

The main and mini timelines each track from scroll geometry whether the end is visible. They scroll to the end only for the first display and for items added while following. When a user action or source navigation leaves the end, following stops. It resumes only on return to the end.

7.1 Sync between Macs

Sync/ implements sync between Macs through a folder that the user chooses. Lore does not connect to the network. It only reads and writes encrypted files that the folder provider transports.

  • Recording changes. v10-sync creates INSERT, UPDATE, and DELETE triggers on life_log_utterances, life_log_memos, sessions, and vocabulary. They record into sync_outbox(entity, record_id, changed_at) only while sync_control has enabled = 1 and suppressed = 0. The MCP server does not write user records, so no other process feeds the outbox. Deletion by retention period, the two bulk deletions, and applying changes from another Mac run inside one transaction with suppressed = 1 and never reach the outbox. The full reset calls SyncStore.reset first, which disables sync and empties the outbox.
  • Export. SyncEngine.export reads the outbox and builds a batch of at most 1000 records: an upsert with the current column values when the row still exists, a tombstone when it does not. It writes a temporary file and renames it to <folder>/Lore Sync/devices/<device-id>/<10-digit seq>.loresync. In the following transaction it deletes only the outbox rows whose changed_at is unchanged since the export and records the versions in sync_versions. The sequence number is the larger of the next number in the database and the highest existing file number plus 1, so a crash after the file write never reuses a number.
  • Import. For every device directory except its own (directories named with a UUID, in sorted order), Lore reads files in sequence from the next number in sync_cursors. Decryption, verification, applying, and the cursor update happen in one transaction. A failing file stops the import for that device and makes its later files wait. For an iCloud Drive .icloud placeholder, Lore requests the download and continues at the next sync.
  • Conflicts. Versions compare lexicographically as (changed_at, device_id), and only the newer one is applied (last writer wins). Outbox rows that are not exported yet count as this Mac's version in the comparison. Tombstones stay in sync_versions with deleted = 1 so an older upsert cannot revive the row.
  • Columns. An utterance sends only id, the times, and text. Another Mac stores it with audio_chunk_id and calendar_event_id as NULL, which is why v10-sync makes life_log_utterances.audio_chunk_id nullable and rebuilds the FTS. History sends every column of sessions, vocabulary every column of vocabulary, and memos every column. Audio, calendar snapshots, generated notes, AI event exclusions, modes, settings, and API keys are out of scope.
  • File format. The LORESYNC magic, a 1-byte format version, the header JSON length (UInt32 big endian), the header JSON (device, seq), and an AES-GCM combined box (12-byte nonce, ciphertext, 16-byte tag). Everything from the magic through the header JSON is authenticated as associated data. The plaintext is the batch JSON compressed with LZFSE. Lore Sync/keycheck.loresync seals a known plaintext with the same key and verifies the sync code on join.
  • Key and state. The 256-bit key is stored as the sync code string in SecretStore under sync.key, a generic password that is not synchronizable. The sync code is the 32 key bytes plus the first 2 bytes of their SHA-256, encoded in RFC 4648 base32 without padding and grouped by 4 characters with hyphens. Decoding ignores case, whitespace, and hyphens. The device ID, folder bookmark, next sequence number, last sync time, and last error live in the single row of sync_control. Turning off sync and the full reset clear that row and empty sync_outbox, sync_versions, and sync_cursors.
  • Triggers for running. SyncCoordinator (@MainActor) observes outbox changes with GRDB DatabaseRegionObservation and exports after a 5-second debounce. It exports and imports at launch, on app activation, on a 120-second timer, and on "Sync Now". When an import changed rows, it reloads the history, the vocabulary, and the Life Log.

10. Automation boundary

LifeLogTextExporter merges consecutive utterances less than 90 seconds apart into one paragraph unless another kind of item separates them. The timeline itself keeps one row per utterance. LifeLogExportSheet limits the preview to 4,000 characters, also in the background.

lore-mcp uses LoreAutomationService. It provides the list of days with records, the structured entries of a range, the day export, cross-record search, and the AI notes of a range (aiNotes, marked generated: true with their stale reasons), all read-only with respect to user records. The range read uses the same LifeLogStore.day as the screen for each day, so the dictation-first utterance projection and the participation filter apply unchanged. It offers no write to Lore. Opening the database still runs migrations and backups (section 7).

Event details reach automation clients without being stored, and only through the app. macOS decides calendar access by the responsible process, and lore-mcp runs as a child of the AI client, so EventKit in lore-mcp asks for the client's permission. On macOS 26 that request returns false without a dialog, both under a client app with no calendar usage string and under one that has it. So lore-mcp never reads EventKit. It asks the running Lore.app, which the user already allowed, over a local Mach port.

  • Boundary. LoreAppEventDetailsServer registers the CFMessagePort named dev.agatan.Lore.event-details on the main run loop, only in the production bundle and not in the screenshot demo. LoreAppEventDetails (in lore-mcp) is the client and implements CalendarEventDetailsRangeReading. The port exists only while the app runs, so nothing is left behind after a crash, and no launchd job, socket file, or entitlement is involved.
  • Data shape. The request is the JSON of EventDetailsRequest (start, end). The reply is the JSON of EventDetailsReply: details with [CalendarEventDetails], or noCalendarAccess. CalendarEventDetails and CalendarAttendee are Codable. The join link is not sent: decoding rebuilds it with the same ConferenceLink.first(url:location:notes:).
  • App side. The callback runs on the main thread. It replies noCalendarAccess unless the app has full calendar access. Otherwise it reads the range synchronously with its own EKEventStore through CalendarProvider.details(in:start:end:selectedCalendars:), using the calendars selected in the Life Log settings of the app, so the caller cannot choose calendars. init(settings:) builds this read, and init(portName:read:) takes another read for tests. The app never asks for calendar access here, and keeps nothing.
  • Client side. LoreAppEventDetails throws EventDetailsUnavailable: loreNotRunning when no port has the name, noCalendarAccess from the reply, noAnswer(code) when CFMessagePortSendRequest fails or times out (1 second to send, 10 seconds to answer), and invalidReply when the reply does not decode.
  • Service. LoreAutomationService takes an optional reader. lore-mcp passes LoreAppEventDetails. For each day it reads, range asks for that day's events with one details(start:end:) call over the span of the events, and matches the results to the snapshots by occurrence(eventID:startsAt:). exportDay does the same only when Options.includesEventDetails is set, and passes the matches to LifeLogTextExporter.render(eventDetails:), which prints the description and attendees under the event. Both return EventDetailsOutcome, which holds the result and the first EventDetailsUnavailable of the request. After a failure the remaining days are not asked. lore-mcp returns the reason as a second text item of the tool result.
  • Fields. LifeLogEntry omits every field that is nil or blank (optionals are encoded only when present, and a blank description, name, or email counts as nil), so nothing is an empty string. externalIdentifier comes from the snapshot (falling back to the EventKit value), so it is present for an event that EventKit no longer has. event-details without calendar is rejected with AutomationError.eventDetailsNeedCalendar, so a client does not get a silent no-op.
  • Trust. Any process of the same user can look up the port, as it can start lore-mcp or read the database, and a process that registers the name before Lore can answer in its place, as it could rewrite the database. Neither side checks the peer's code signature, because lore-mcp itself answers any process that starts it. Details never enter LifeLogStore, a backup, sync, or Life Log AI input.

App Intents run only the capture start, stop, pause, and resume after AppEnvironment.boot() completes. The start and resume actions use foreground mode because they handle the microphone, and the stop and pause actions use background mode. Pause and resume call the same AppEnvironment methods as the UI. Running from Shortcuts needs a bundle signature that macOS can verify, so the build prefers a valid Apple Development identity over a self-signed one. The public actions and tool schemas are listed in the external specification.

Guidance that an AI client needs lives in the MCP server itself: the instructions of the initialize result and the tool descriptions. Lore writes nothing into the user's home folder for it. The Integrations page only shows the path of lore-mcp inside the app bundle and copies the registration command.

11. Concurrency and error reporting

  • UI state and the coordinators are fixed to @MainActor.
  • EventKit reads are serialized by the CalendarProvider actor and database operations by the GRDB DatabaseQueue.
  • The speech recognition and LLM protocols and the domain values are Sendable by default, and long work is owned and canceled as a Task.
  • A recoverable failure goes to one of: the history status, a message on screen, or isError in MCP. Text content, API keys, and vocabulary never go to the log.
  • WindowActivityLog writes each window's key, screen change, end of live resize, and close, and the HUD's show and hide, to the unified log (dev.agatan.Lore, category ui) with the window identifier or class, frame, and screen name, so a crash inside AppKit or SwiftUI layout can be traced to the windows that were open. It never logs window titles.
