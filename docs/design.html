KoeAppはMenuBarExtra、main、settings、life-log mini、all TODOのwindowを定義します。AppEnvironmentは@MainActor @Observableのcomposition rootです。

UI test用の明示的な遷移がなければmainSection = .lifeLogとしてmain windowを開きます。

LifeLogWindowとLifeLogMiniWindowは表示開始時にLifeLogCoordinator.followCurrentDay()で今日を読み込み、初回だけtimeline末尾へscrollします。以後のreloadでは閲覧位置を動かさず、TODOの出典移動はsourceNavigationRevisionで明示的に行います。

終了時は進行中操作をinterruptし、audio writerのcommitと必要なDB保存だけを短時間待ちます。派生処理は起動せず、確定済みchunkは次回起動時に再処理します。20秒deadlineは最終保険です。

4. 音声入力flow

Hotkey / UI
→
SessionContext固定
→
AudioCapture + STT
→
rawをinterrupted保存
→
FormattingPolicy + LLM
→
TextInserter

Context

対象app、mode、共通rule、語彙、STT/LLMを録音開始時に固定します。

Recovery

LLM前にrawを保存。整形失敗はraw、挿入失敗はclipboardへ退避します。

Storage

通常の音声入力はaudio fileを作りません。履歴にはtext、snapshot、状態、計測値を保存します。

DictationCoordinatorのcapture destinationは通常音声入力とボイスメモです。ボイスメモは同じAudioCapture、STT、HUDを使いますが、SessionDraft、LLM、HistoryStore、TextInserterを通らず、確定した生textをLifeLogCoordinator.addMemoへ一度だけ渡します。AppEnvironmentは開始前にlife-log captureの安全な一時停止を待ち、終了結果にかかわらず記録意図に従って再開します。LifeLogMemoComposerの音声ボタンとglobal hotkeyはどちらもAppEnvironment.toggleVoiceMemoを呼び、Viewは準備中と録音中のstateだけを投影します。

5. Life-log flow

Capture request
→
30秒 .m4a commit
→
AudioChunk保存
→
連続STTでUtterance保存
→
Calendar / Conversation
→
Summary / draft TODO
  • 音声入力とは独立したcaptureとSpeechAnalyzer sessionを持ちます。
  • 30秒chunkは復旧単位で、認識sessionは記録開始から停止まで維持します。
  • 音声入力と重なる区間もraw audioと認識済みutteranceを保存します。成功したSessionRecordをtimeline、検索、exportの正本として重なるlife-log utteranceを除外します。Summary/TODOは通常音声入力も重なるlife-log utteranceも使いません。Cancelled/failed sessionではlife-log utteranceを残します。
  • pending chunkは起動後に再処理し、無音はpeak levelで除外します。
  • Audio保持policyは「処理後削除」を既定とし、「7日」「30日」を選択可能にします。削除可能なのはtranscription_state = transcribedかつprocessing_state = extractedのchunkだけです。「処理後削除」は両状態の保存完了後、「7日」「30日」はさらにcapture_ended_atから指定日数の経過後にfileを削除します。DBのchunk metadataと派生dataは削除しません。
  • LifeLogStoreが処理状態と保持policyから削除可能なaudio URLを決定し、AppEnvironmentはその結果だけをfile systemから削除します。Policy変更時と起動時に同じuse caseを実行し、未処理・失敗chunkを期間だけで削除しない不変条件を一か所に置きます。
  • ContinuousAudioCaptureは実際のaudio writerの開始・停止をonRunningChangedで通知し、LifeLogCoordinator.isCapturingだけを全UIの実録音状態へ投影します。さらにAVAudioEngineConfigurationChangeを再接続可能なfailureとして通知します。LifeLogCoordinatorは旧writerとSTT sessionの終了を待ち、記録意図が残り、sleepまたはボイスメモによる一時停止中でなければbackoff付きで再接続します。マイク権限拒否だけは再試行しません。
  • 設定画面のcalendar手動再取得は、選択日のsnapshot保存、timeline再読込、月間activity更新を一つのuse caseとして実行します。発話と予定は前後2分で関連付け、conversationは90秒の無発話で分割します。
  • Life-log発話またはmemoの差分検出後、その日のlife-log発話、memo、予定からsummaryとdraft TODOを再生成します。通常音声入力は入力にもtriggerにも使わず、app終了時は派生を開始しません。
  • LifeLogDerivationServiceにはsummaryの基準時点を渡します。Timeline入力のcalendar eventを基準時点との比較で終了済み、進行中、これからに分類し、system instructionにも現在日時と未来予定を過去形にしない制約を加えます。日付変更時は前日の差分がなくても全予定を含むfinal summaryを再生成します。

6. Engines

Backend Adapter / Endpoint Mac外へ送信
Apple Foundation Models FoundationModelsLlm なし
Ollama RemoteLlm / localhost:11434/v1 なし

OpenAI / Anthropic / Gemini RemoteLlm 明示選択時
Groq GroqLlm 明示選択時

FormattingPromptは通常textか、名前とfield型を持つ構造化出力contractを明示します。LifeLogDerivationServiceはsummary/TODOのJSON contractを宣言し、model判定を持ちません。GroqLlmはこれを温度0、推論本文なし、選択modelが対応する最小の推論量と最も強いJSON制約へ変換します。GPT-OSSはreasoning_effort = lowとstrict JSON Schema、reasoningを無効化できるmodelは無効化とJSON Object Mode、それ以外は未対応parameterを送らずJSON Object Modeを使います。全経路で同じapp側decodeを最終検証とし、通常の文章変換は温度0とprovider既定の推論量を維持します。

音声入力とlife logはprovider/modelを別設定にします。語彙候補のanalysisLlmは常にオンデバイスです。

7. Persistence

Store Tables
HistoryStore sessions, sessions_fts
ModeStore / SharedRulesStore modes, meta
VocabularyStore vocabulary, vocab_suggestions
LifeLogStore audio chunks、calendar snapshots、conversations、utterances、memos、todos、daily summariesとFTS
LlmUsageStore llm_usage_events

利用状況の録音時間はDailyRecordingDuration.aggregateで重なる区間を先に統合してから日境界で分割します。音声入力はHistoryStoreの実録音区間、life logはLifeLogStoreのtimelineに採用されたutterance区間を入力とし、LifeLogSpeechProjectionと同じ規則で成功した音声入力と重なるutteranceを除外します。復旧用audio chunkの無音区間や同一区間の重複は利用時間へ加算しません。

DBはApplication Support/Koe/koe.sqlite、migrationはv1〜v8です。既存DBはmigration前と1日1回backupし、Backups/の最新7fileを保持します。全data削除はbackupも削除します。

8. 設定、秘密、process間同期

  • AppSettings.Storageをsuite dev.agatan.KoeのUserDefaults key koe.settings.v1へJSON保存します。
  • Provider/modelは音声入力とlife logで分離します。通常音声入力、life-log capture、mini window、ボイスメモのhotkey、保持期間、calendar filter、summary間隔をここに入れます。Mini windowは常時手前を不変条件とし、表示levelの設定は持ちません。Color themeも設定として保持せず、KoeThemeの固定brand tokenを使います。
  • API keyだけはKeychainへ保存します。
  • CLI/MCPによるTODO・prompt変更はDistributed Notificationでappへ通知します。

10. 自動化境界

App Intents、CLI、MCPを公開します。CLI/MCPはKoeAutomationServiceを共有し、日別export、open TODO export、横断検索、TODO CRUD、summary/TODO prompt更新を提供します。公開commandとtool schemaは外部仕様に列挙します。

11. 並行実行とerror表示

  • UI stateとcoordinatorはMainActor、Calendarはactor、DBはDatabaseQueueで直列化します。
  • 長時間処理は所有Taskでcancelします。
  • 失敗は履歴status、画面、MCPのisError、CLIのstderr/exit 1のいずれかへ出し、本文やsecretをlogへ出しません。
