3. Processと起動

LoreAppはMenuBarExtraを常設します。LoreApplicationDelegateはwindow sceneの生成有無に依存せずruntimeを起動し、LoreWindowPresenterがmain、settings、life-log miniの各windowを一意に所有します。Main windowは1680×960 ptで生成します。Presenterはwindowをkey windowにした後、activation policyの切替がwindow serverへ反映されるまで短く待ち、activeになるまで最大1秒だけactivateを再要求します。明示的な表示要求では対象windowを前面にします。UI、menu、hotkeyはAppEnvironmentの同じ表示actionを呼び、同種windowを重複生成しません。AppEnvironmentは@MainActor @Observableのcomposition rootです。

UI test用の明示的なsettings遷移がなければmainSection = .lifeLogとしてmain windowを開きます。

起動時のcaptureRequestedは必ずfalseです。以前のruntime記録意図を設定から復元せず、明示的なUI、hotkey、App Intentと、有効な自動記録scheduleだけが新しい記録意図を作ります。

自動記録は三層に分けます。Domain/LifeLogScheduleは曜日・開始分・終了分だけを持つ値で、window(containing:)とnextTransition(after:)をCalendar経由で計算します（日付またぎとDSTを含む）。Domain/LifeLogScheduleControllerは「scheduleが開始した記録か」「手動停止で抑止中の時間帯の開始時刻」だけを状態に持つ純粋な状態機械で、現在時刻と記録意図から開始・停止・何もしないを決めます。AppEnvironmentは起動完了、設定変更、wake、NSSystemClockDidChange、NSSystemTimeZoneDidChangeで評価し、次の切替時刻までsleepする単一のTaskを張り直します。Polling loopは使いません。手動の開始・停止はsetLifeLogCaptureEnabledから状態機械へ通知し、scheduleの開始は同じcapture遷移をbyScheduleで通します。録音audio保存への同意がなければscheduleは開始せず、bannerで手動開始を案内します。

LifeLogWindowとLifeLogMiniWindowは今日を読み込み、初回だけtimeline末尾へscrollします。

終了時は進行中操作をinterruptし、audio writerのcommitと必要なDB保存だけを短時間待ちます。確定済みchunkは次回起動時に再処理します。20秒deadlineは最終保険です。

→

→

→

→
Durable audioを遅延STT
→

Life logから要約、話題、TODOを生成するLLM経路は持ちません。振り返りや作業整理は外部の汎用AIがCLI/MCPの日別exportと検索を読む前提で、Loreはsource of truthの記録、検索、書き出しだけを担います。

  • 音声入力とは独立してaudioを連続耐久化し、Life Log STTはadaptiveな発話burstごとのpreviewと確定jobです。
  • Audio chunkは復旧単位です。30秒ごとに加えてburst確定時にもwriter queue上の入力を原子的にcommitし、最終認識は対応するcommit callback後に開始します。Checkpoint後は定期rotationを30秒後へ再設定し、同時rotationによる空chunkを作りません。
  • AdaptiveSpeechSegmenterはUI表示用levelではなく入力signalの線形RMSを使い、起動直後にbackground noise floorを校正して非発話中も更新します。約-50 dBFSの絶対下限とnoise floorに対する差・倍率が250ms継続した場合だけburstを開始し、30秒未満は1.5秒、30秒以上は1秒の無音でflushします。Flush時は累積有声時間0.5秒以上かつ有声比率20%以上をSpeechBurstEvidenceの不変条件とし、満たさない候補はSTTとcheckpointへ渡しません。Whisper.cppでは有効な発話の開始1.5秒後から、前のpreviewが完了している場合に1.5秒ごとに直近5秒を認識し、暫定textは永続化しません。
  • Jobは参照audioのcommit後に開始します。Timestampはcapture開始時刻とaudio offsetから導出します。語彙は録音session開始時にsnapshot化し、保存audioの再処理では最新の有効語彙を使います。
  • 音声入力と重なる区間もraw audioと認識済みutteranceを保存します。成功したSessionRecordをtimeline、検索、exportの正本として重なるlife-log utteranceを除外します。Cancelled/failed sessionではlife-log utteranceを残します。
  • pending chunkは起動後に再処理します。保存済みpeak levelはUI用の正規化levelのまま保持し、その尺度で約-50 dBFS未満の明確な無音chunkを除外します。それ以外も保存audioを線形RMSで同じsegmenterへ戻し、有効なburstだけを個別にSTTへ渡します。
  • Audio保持policyは「処理後削除」を既定とし、「7日」「30日」を選択可能にします。削除可能なのはtranscription_state = transcribedかつprocessing_state = extractedのchunkだけです。processing_state = extractedは発話の保存まで完了したことを表し、旧版の派生処理状態名を保存互換のため流用します。「処理後削除」は両状態の保存完了後、「7日」「30日」はさらにcapture_ended_atから指定日数の経過後にfileを削除します。DBのchunk metadataと発話は削除しません。
  • LifeLogStoreが処理状態と保持policyから削除可能なaudio URLを決定し、AppEnvironmentはその結果だけをfile systemから削除します。Policy変更時と起動時に同じuse caseを実行し、未処理・失敗chunkを期間だけで削除しない不変条件を一か所に置きます。
  • ContinuousAudioCaptureは実際のaudio writerの開始・停止を通知します。LifeLogCoordinatorは旧writerとSTT sessionの終了を待ち、同じprocessの記録意図が残り、sleepまたはボイスメモによる一時停止中でなければbackoff付きで再接続します。マイク権限拒否だけは再試行しません。
  • 設定画面のcalendar手動再取得は、選択日のsnapshot保存、timeline再読込、月間activity更新を一つのuse caseとして実行します。発話と予定は前後2分で関連付けます。

6. Engines

音声入力・ボイスメモ用とlife logのpreview・確定job用のSttEngineを、それぞれSpeechAnalyzerSttまたはlocal download済みwhisper.cppから選びます。セッションとjobは開始時のengineを最後まで使います。Audioは送信しません。

WhisperCppSttはLarge v3 Turbo Q5_0 574 MBを既定とし、非Turbo Large v3 Q5_0も選べるcatalog、download、cancel、SHA-256検証、削除を所有します。公式XCFrameworkのC APIをprocess内から直接呼び、GGML modelをMetalとCPUで実行します。Core ML modelとANE specialization、Homebrewや外部CLIへの依存は持ちません。Decode時はspecial tokenを出力せず、engine境界でもcontrol/timestamp tokenを除去します。Read/UI側の補正や既存dataの自動書換えは持ちません。

GGML重みはWhisperModelCacheがfileごとに一つだけloadし、全stateが手放した時点で解放します。EngineRegistryは音声入力用とlife log用に別のWhisperCppSttを持ち、各自の推論stateで動くため両用途は互いを待ちません。同じstateでの推論と結果読取りはactorとstate handleの排他で直列実行し、実行中jobは自分のstateと重みを完了まで保持します。音声入力はcaptureFormatで録音を待たせずにstateの準備を開始し、10分のidle後に音声入力用stateだけを解放します。Life log用stateは記録停止の完了時に解放します。WhisperInputPolicyが前後の無音を除いた範囲と、並び順を保ってtoken上限へ収めた語彙promptを決め、segment offsetへ除いた長さを加えます。Prompt全体の写しだけのsegmentは除きます。Control/timestamp tokenと、独立した文として現れる既知の定型hallucination「ご視聴ありがとうございました」はengine境界で除去し、後続する実発話は保持します。LifeLogCoordinatorはSpeechBurstEvidenceが有効になった発話だけを対象に、発話検出から1.5秒後、前のpreviewが完了していれば1.5秒ごとに直近5秒のsnapshotを同じengineへ渡し、ephemeralなliveTranscriptだけを更新します。実行中previewへ新しいsnapshotを重ねず、burst確定時はpreviewのcancel完了後に最終認識を優先します。Preview失敗はlogへ残しますがchunkをfailedにしません。有効なburst確定時だけContinuousAudioCaptureへcheckpointを要求し、永続化済みaudioによる最終認識だけを正本として保存します。

Main/mini timelineはscroll geometryから末尾表示を保持し、初回と追従中のitem追加だけ末尾へscrollします。利用者操作またはsource navigationで末尾を離れた場合は追従を止め、末尾へ戻った時だけ再開します。

Named migrationはv1からv11です。v9-remove-todo-summary-usageはTODO、日次要約、token集計、会話区切りのtableとFTSを削除し、life_log_utterancesをconversation_idなしで作り直してFTSを再構築します。削除前の内容はmigration直前backupに残ります。v10-syncは同期用tableとtriggerを追加し、life_log_utterances.audio_chunk_idをNULL許容へ作り直します（7.1）。v11-remove-vocab-suggestionsは履歴からの語彙候補を廃止したためvocab_suggestionsを削除し、候補から登録済みの語彙はvocabularyに残します。

DBはApplication Support/Lore/lore.sqlite、whisper.cpp modelと途中downloadはApplication Support/Lore/Models/WhisperCpp/です。既存DBはmigration前と1日1回backupし、最新7fileを保持します。全data削除はbackup、新旧model、途中fileも削除します。

7.1 Mac間同期

Sync/は利用者が選んだfolderを経由するMac間同期です。Loreはnetworkへ接続せず、folderの提供元が運ぶ暗号化fileだけを読み書きします。

  • 変更の記録: v10-syncがlife_log_utterances、life_log_memos、sessions、vocabularyのINSERT/UPDATE/DELETE triggerを作り、sync_controlのenabled=1かつsuppressed=0の間だけsync_outbox(entity, record_id, changed_at)へ記録します。CLI/MCPは読み取り専用のため、別processからの書き込みはありません。保持期間による削除、一括削除、全data削除、他のMacからの適用はsuppressed=1の同じtransaction内で行い、outboxへ載せません。
  • 書き出し: SyncEngine.exportはoutboxを読み、行が残っていれば現在の列値をupsert、無ければtombstoneにしたbatchを作ります。<folder>/Lore Sync/devices/<device-id>/<10桁seq>.loresyncへ一時fileを書いてrenameし、その後のtransactionで、書き出し時とchanged_atが同じoutbox行だけを消してsync_versionsへ版を記録します。seqはDBの次番号と既存file最大値+1の大きい方で、file書込後のcrashでも番号を再利用しません。
  • 取り込み: 自分以外のdevice directoryをsync_cursorsの次seqから連番で読みます。復号・検証・適用とcursor更新を1 transactionで行い、失敗したfileで止めて同じdeviceの後続を待たせます。iCloud Driveの.icloud placeholderはdownloadを要求して次回へ回します。
  • 競合: 版は(changed_at, device_id)の辞書順で比較し、新しい方だけを適用します（後勝ち）。未書き出しのoutbox行も自分の版として比較に含めます。Tombstoneもsync_versionsにdeleted=1で残し、古いupsertで復活させません。
  • 列の範囲: 発話はid、時刻、textだけを送り、他のMacではaudio_chunk_idとcalendar_event_idをNULLで保存します。このためv10-syncはlife_log_utterances.audio_chunk_idをNULL許容へ作り直し、FTSを再構築します。履歴はsessionsの全列、語彙はvocabularyの全列、memoは全列です。Audio、calendar snapshot、mode、設定、API keyは対象外です。
  • file形式: LORESYNC magic、format version 1 byte、header JSON長(UInt32 big endian)、header JSON（device, seq）、AES-GCM combined box（nonce 12 byte + 暗号文 + tag 16 byte）。Magicからheader JSONまでをassociated dataとして認証します。平文はLZFSE圧縮したbatch JSONです。Lore Sync/keycheck.loresyncは既知の平文を同じ鍵で封じたfileで、参加時に同期コードを検証します。
  • 鍵と状態: 256-bit鍵はSecretStoreのsync.key（non-synchronizable generic password）に同期コード文字列として保存します。同期コードは鍵32 byteとSHA-256先頭2 byteをRFC 4648 base32にして4文字ずつ区切ったものです。Device ID、folder bookmark、次seq、最終同期時刻、最後のerrorはsync_controlの1行に置き、全data削除と同期解除で消します。
  • 実行契機: SyncCoordinator(@MainActor)はoutboxの変更をGRDBのDatabaseRegionObservationで受けて5秒debounceで書き出し、起動時、app activation、120秒timer、「今すぐ同期」で書き出しと取り込みを行います。取り込みで行が変わった場合は履歴、語彙、life logを再読込します。

8. 設定、秘密、process間同期

  • AppSettings.StorageをUserDefaultsへ保存しますが、runtimeのcaptureRequestedは永続化しません。自動記録schedule（lifeLogSchedule、既定は無効）は設定として保存します。
  • dictationSttBackendとlifeLogSttBackendは用途ごとのengine選択です。whisper.cpp modelは両用途で共有し、保存keyは共有化前のlifeLogWhisperModelを維持します。Life log認識言語はlife logだけに置きます。
  • 認識言語の既定値は表示言語を固定hintへ解決し、明示的な自動判定も選べます。
  • GGML model本体と途中downloadは専用directoryへ置き、全data削除に含めます。
  • 表示言語はlife log設定が明示する解決以外ではSTT locale、prompt、保存data、automation contractへ伝播させません。
  • View以外で組み立てる利用者向け文言（error、状態表示、notice）はString(lore:)で同じLocalizable.stringsから引きます。AppEnvironmentが設定の表示言語をLoreLocalizationへ写すため、SwiftUIへ注入したLocaleと同じ言語になります。作った時点の言語で文字列になり、履歴へ残す理由もその言語のまま保存します。ログ、LLMへ送るprompt、CLI/MCPの機械向け出力は翻訳しません。LocalizationCoverageTestsが三言語のkey・format specifierの一致と、UI/Appの日本語literalがkeyにあることを検査します。
  • API keyだけはKeychainへ保存します。廃止したlife log用provider、prompt、要約間隔のkeyは読み捨て、保存し直した時点で消えます。

10. 自動化境界

App Intents、CLI、MCPを公開します。CLI/MCPはLoreAutomationServiceを共有し、記録がある日の一覧、期間の構造化項目、日別export、横断検索を読み取り専用で提供します。期間取得は画面と同じLifeLogStore.dayを日ごとに読み、音声入力優先の発話projectionと参加中予定filterをそのまま使います。Loreへの書き込みは提供しません。App IntentsはAppEnvironment.boot()の完了後にcapture開始・終了だけを実行します。開始Actionはマイクを扱うためforeground mode、終了Actionはbackground modeです。Shortcutsからの実行にはmacOSが検証できるbundle署名が必要なため、buildは有効なApple Development identityを自己署名より優先します。公開commandとtool schemaは外部仕様に列挙します。

LifeLogTextExporterは90秒未満の連続発話を別種の表示項目で区切ってまとめます。LifeLogExportSheetはプレビューもbackgroundで4,000文字に制限します。Timelineの予定rowは淡い塗りと左端の色帯で発話と区別します。

11. 並行実行とerror表示

  • UI stateとcoordinatorはMainActor、Calendarはactor、DBはDatabaseQueueで直列化します。
  • 長時間処理は所有Taskでcancelします。
  • 失敗は履歴status、画面、MCPのisError、CLIのstderr/exit 1のいずれかへ出し、本文やsecretをlogへ出しません。

13. Test配置

Tests/LoreKitTestsはnoise floor校正と追従、相対level差による発話開始、1.5/1秒tier、whisper.cppの1.5秒preview cadenceと5秒rolling window、5分flushをdomain testで固定します。make ui-testは本番と別のbundle IDを持つ署名済みLoreUITests.appを別process instanceとして起動して主要CUJを検証します。UI test bundleは専用UserDefaultsとインモリDBを使い、global hotkeyと権限監視を起動しません。E2E runnerは専用bundle ID以外のappを終了せず、本番bundle IDを指定された場合は実行を拒否します。同期はSyncTestsが、同期コードとfileの暗号（違う鍵、改ざん、途中まで、新形式）と、2つのin-memory DBと一時folderによる往復（memo・履歴・語彙・発話、後勝ち、tombstone、保持期間と一括削除の非伝播、初回snapshot、読めないfileでのcursor停止、番号の非再利用、解除）、v10-sync migrationを検証します。
